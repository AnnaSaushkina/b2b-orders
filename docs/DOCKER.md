# Docker

## Состав

```
├── postgres:18   → localhost:5432   (данные: named volume pg-data)
├── redis:7       → localhost:6379   (заготовка под фоновую очередь)
├── API (NestJS)  → localhost:4000
└── клиент        → localhost:3000
```

## Два режима

### Режим 1 — инфраструктура в контейнерах, приложение на хосте

```bash
docker compose up -d
pnpm dev
```

Повседневная разработка: hot-reload клиента и API, БД по `localhost:5432`.

### Режим 2 — всё в контейнерах, включая API

```bash
docker compose -f docker-compose.yml -f docker-compose.app.yml up -d --build
```

Прод-подобная сборка. API ходит в БД по `postgres:5432` — по имени сервиса во внутренней
сети Compose, а не по `localhost` (внутри контейнера `localhost` — это сам контейнер).

Остановить: `docker compose down` (данные в volume останутся), `down -v` — вместе с данными.

## Решения

- **Базовый файл + надстройка вместо двух самодостаточных.** `docker-compose.yml` описывает
  только инфраструктуру, `docker-compose.app.yml` добавляет к ней `api`. Compose сливает файлы
  по порядку (`-f ... -f ...`), PostgreSQL и Redis не дублируются между режимами.
- **`depends_on: condition: service_healthy`.** API стартует не когда контейнер БД запустился,
  а когда healthcheck подтвердил готовность принимать соединения.
- **`PGDATA` задан явно.** PostgreSQL 18 сменил дефолтный путь данных на
  `/var/lib/postgresql/18/docker`; фиксация классического пути делает volume
  версионно-независимым.
- **Многостадийный Dockerfile на debian-slim, не alpine.** Prisma тянет нативный engine и
  требует openssl — на glibc меньше сюрпризов, чем на musl.
- **`prisma migrate deploy` при старте контейнера**, а не `db push`: схема раскатывается
  версионированными миграциями.

## Диагностика

- **`EADDRINUSE :::4000`** — контейнерный API (режим 2) и хостовый `pnpm dev` делят один
  host-порт. Перед запуском режима 1 нужно погасить контейнерный API.
- **Два PostgreSQL на `:5432`** — нативная установка и контейнер одновременно. `localhost`
  резолвится в `127.0.0.1`, который занимает нативный сервер, и запросы уходят не в ту базу.
- **Пустая база в GUI-клиенте** — данные лежат в `marven → public`, а не в служебной базе
  `postgres`. Один сервер, разные базы.
